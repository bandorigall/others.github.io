■ 질문 수 줄이기 — 원본 엔진 직접 구동 결과 (2026-08-01 3차) ★중요
  사용자가 "원본은 45명에 137회밖에 안 걸린다"고 해서 원본 엔진(fnc_main_v4_5.js)을
  node 에서 그대로 돌려 확인했다. 결과적으로 사용자 말이 맞았고 원인은 두 가지였다.

  (1) 비김의 동점 링크가 누적된다
      원본은 ary_EqualData 로 묶인 캐릭터를 이후 모든 병합에서 질문 없이 딸려보낸다.
      우리도 state.eqLink + merge() 의 drain() 으로 이식. 60명 기준
      비김 10%면 282→226, 20%면 198 로 떨어진다.
      ※ 원본은 링크만 보고 무조건 딸려보내 순서가 틀어질 수 있는데,
        우리는 '다음 캐릭터가 실제 그 짝인지' 확인한다. 그래서 원본보다 7% 정도
        질문이 많지만 정확하다. 이 검사를 빼지 말 것.

  (2) ★원본은 캐릭터를 섞지 않는다 (main.js/data.js 전체 grep 으로 확인.
      Math.random 은 '어떤 일러스트를 보여줄지' 고르는 2군데뿐)
      즉 항상 밴드 순서로 시작한다. 병합정렬은 초기 순서가 취향과 비슷할수록
      질문이 급감하므로, 밴드 단위로 취향이 갈리는 사람은 크게 이득을 본다.
      원본 45명 실측: 취향이 목록 순서와 동일 136회 / 밴드 순서 유지 147회
                      / 밴드끼리만 뭉침 169회 / 완전 무작위 193회
      → 우리도 셔플을 완전히 버렸다. shuffle() 함수도 삭제.
      ※ 단, '밴드끼리 묶는' 배치는 2026-08-01 사용자 지시로 제거했다.
        밴드 군집의 이득은 밴드 단위로 취향이 갈리는 사람에게만 발생하는데
        실제로는 그렇지 않다는 판단. 지금은 데이터 순서 그대로 시작한다.
        [금지] 셔플·밴드 군집 모두 임의로 되살리지 말 것.
        같은 취향을 두 버전에 먹여 비교(60명):
            무작위 취향     282 → 281  (손해 없음)
            밴드끼리 뭉침   281 → 248
            밴드 순서 일치  282 → 210
      ※ 주의: 그냥 '셔플만 제거'하면 characters.json 순서(=생일순)가 되어
        밴드가 뒤섞이므로 이득이 없다(283→281). 반드시 밴드로 묶어야 한다.

■ 알고리즘 조사 기록 (2026-08-01) — 다시 뒤집지 말 것
  1) 참고 사이트(garupasorter.tumblr.com)의 실제 코드를 받아 확인한 결과
     2008년 K-Factory 제 '캐릭터 소터'로, **토너먼트가 아니라 병합정렬**이다.
     (fnc_Sort/fnc_CountUp 이 좌우 리스트를 머지하는 구조, ary_EqualData=비김, back_*=Undo)
  2) 정보이론 하한: 60명 전체 순위 확정에 필요한 정보량은 log2(60!) = 272.1 비트.
     → 이진 비교로는 최소 273회. 현재 병합정렬 평균 282회는 하한 대비 +3.3%로 사실상 최적.
     즉 "전체 순위를 유지하면서 질문을 크게 줄이는 방법은 원리적으로 없다."
  3) Elo + 스위스 페어링(근사) 시뮬레이션 200회 — 채택하지 않음:
        라운드 질문수 스피어만 1위적중 상위10일치
          4    120    0.842    31%    64%
          5    150    0.885    54%    75%
          6    180    0.911   100%    75%
         10    300    0.958   100%    84%
     300문항을 써도 병합정렬(282문항, 완전정확)보다 나쁘다.
  4) 채택안 — 토너먼트 브래킷을 우승자 제거하며 반복(상위 K명 정확).
     이미 답한 비교는 캐시되므로 2위부터는 직전 우승자 경로만 다시 물어본다.
        K=3 94문항 / K=5 116 / K=10 153 / K=20 213 / 전체 282  (모두 정확도 100%)
     → TOP10(약 150) / TOP20(약 215) / 전체(약 280) 3모드로 제공.

■ 정렬 알고리즘 (핵심 결정)
  상향식 병합정렬 + '답변 로그 재생' 방식.
    - 비교 결과를 answers 배열에 순서대로 쌓고, 화면을 그릴 때마다
      정렬을 처음부터 다시 돌린다. 답 없는 쌍을 만나면 예외를 던져
      그 쌍을 질문으로 띄운다.
    - 덕분에 되돌리기 = 로그 pop 후 재실행, 이어하기 = 로그만 저장.
      상태머신/스택 저장 같은 복잡한 구조가 필요 없다.
    - 60명 재정렬은 1ms 미만이라 매 질문마다 다시 돌려도 무방.
  ★ 검증(node): 알고리즘 단위 시뮬레이션 + app.js 를 DOM 스텁으로 실제 구동하는
    통합 테스트 둘 다 통과. (스크립트는 임시폴더에 있었으므로 필요하면 재작성)
      단위   : 완전순서 300회 정확 정렬(평균 281.8, 최대 293) / 비김 300회 정상 종료
      통합   : TOP10 152문항·TOP20 213·전체 283, 세 모드 모두 순위 불일치 0/20
      이어하기: 30문항 진행 → 재부팅 → 이어하기 → 완주, 결과 정확 확인
    ※ 통합 테스트에서 실제 버그를 하나 잡았다. 모드 도입 후 EST_TOTAL 전역을
      MODES[].est 로 바꿨는데 '이어하기' 진행률 계산 한 곳이 옛 이름을 참조해
      저장 기록이 있을 때만 시작 화면이 죽었다. 저장이 걸린 경로는 반드시 테스트할 것.
    진행률 분모 EST_TOTAL = n*ceil(log2 n) - 2^ceil(log2 n) + 1 = 297.
    최대 실측(293)이 분모보다 작으므로 진행률이 100%를 넘지 않는다.
  ★ 비김 처리 (2026-08-01 수정) — 원본과 동작을 맞췄다.
    처음엔 비김에도 왼쪽 한 명만 확정해서 질문 수가 전혀 줄지 않았다.
    원본은 fnc_Sort 의 while(ary_EqualData[...]!=-1) fnc_CountUp() 로
    비김난 두 명을 한 번에 확정한다. 같은 방식으로 고친 뒤 원본과 수치가 일치:
        비김률   0%    10%   20%   35%
        원본    281   256   237   216
        현재    282   257   237   215
    ※ 단 TOP10/TOP20 모드(토너먼트)에서는 비김이 오히려 질문을 조금 늘린다
      (TOP20: 214 → 243). 브래킷에선 비김이 정보를 주지 못하기 때문.
      안내 문구는 '전체 모드에서 비김이 이득'이라고만 적을 것.
